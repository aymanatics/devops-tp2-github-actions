TP1 - Docker
Partie Database
========================

1-1 Pourquoi utiliser -e plutôt que mettre les variables dans le Dockerfile ?

Il est préférable d’utiliser le flag -e pour définir les variables d’environnement au moment du lancement du conteneur plutôt que dans le Dockerfile pour plusieurs raisons :

- Sécurité : éviter de stocker des mots de passe en clair dans l’image
- Flexibilité : on peut changer les paramètres (user, password, db) sans reconstruire l’image
- Réutilisabilité : une même image peut être utilisée dans différents environnements (dev, test, prod)

---

1-2 Pourquoi utiliser un volume pour postgres ?

Un volume est nécessaire pour persister les données de la base de données.

Sans volume :
- les données sont perdues si le conteneur est supprimé

Avec volume :
- les données sont stockées sur le disque de l’hôte
- elles survivent à la suppression/recréation du conteneur

---

1-3 Documentation du conteneur database

Dockerfile utilisé :

FROM postgres:17.2-alpine
COPY initdb/ /docker-entrypoint-initdb.d/

Explication :
- Image de base : postgres alpine (léger)
- Les scripts SQL sont copiés dans le dossier spécial
- PostgreSQL exécute automatiquement les scripts au premier démarrage

---

Commandes utilisées :

Créer le réseau :
docker network create app-network

Build de l’image :
docker build -t my-database .

Lancer le conteneur postgres :
docker run -d \
  --name postgres-db \
  --network app-network \
  -e POSTGRES_DB=db \
  -e POSTGRES_USER=usr \
  -e POSTGRES_PASSWORD=pwd \
  -v "$(pwd)/pgdata:/var/lib/postgresql/data" \
  my-database

Vérifier les conteneurs :
docker ps

Voir les logs :
docker logs postgres-db

Accéder à la base :
docker exec -it postgres-db psql -U usr -d db

- données insérées avec succès

1-4 Pourquoi a-t-on besoin d’un multistage build ? Expliquez chaque étape de ce Dockerfile.

Un multistage build permet de séparer l’environnement de build (compilation) de l’environnement d’exécution.

Avantages :
- image finale plus légère
- moins d’outils inutiles en production
- meilleure sécurité
- image plus propre et optimisée

Explication du Dockerfile :

FROM eclipse-temurin:21-jdk-alpine AS build
- Utilise une image avec le JDK pour compiler le code Java

WORKDIR /usr/src
- Définit le répertoire de travail pour la phase de build

COPY Main.java .
- Copie le fichier source Java dans le conteneur

RUN javac Main.java
- Compile le fichier Java et génère le fichier Main.class

FROM eclipse-temurin:21-jre-alpine
- Démarre une nouvelle image plus légère contenant uniquement le runtime Java

WORKDIR /app
- Définit le répertoire de travail pour l’exécution

COPY --from=build /usr/src/Main.class .
- Copie le fichier compilé depuis l’étape de build vers l’image finale

CMD ["java", "Main"]
- Lance le programme Java au démarrage du conteneur

Backend simple API :

Projet utilisé :

- image de build : eclipse-temurin + Maven
- image de run : eclipse-temurin JRE alpine

Commandes :
docker build -t my-simple-api ./backend-simple-api/simpleapi
docker run --rm -p 8081:8080 --name simple-api my-simple-api

Vérification :
- endpoint disponible sur http://localhost:8081/
- exemple : http://localhost:8081/?name=DevOps

---

Backend API connecté à PostgreSQL :

Configuration `application.yml` :
- host postgres : `postgres-db`
- base : `db`
- utilisateur : `usr`
- mot de passe : `pwd`
- paramètres injectés via variables d’environnement avec valeurs par défaut

Dockerfile utilisé :

FROM maven:3.9.9-eclipse-temurin-21-alpine AS build
WORKDIR /build
COPY pom.xml .
RUN mvn -B dependency:go-offline
COPY src ./src
RUN mvn -B clean package -DskipTests

FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /build/target/*.jar /app/app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]

Pourquoi `mvn dependency:go-offline` ?
- pour télécharger les dépendances Maven avant de copier le code source
- le layer Docker est réutilisé tant que `pom.xml` ne change pas
- les rebuilds sont plus rapides

Commandes :
docker build -t my-backend-api ./simple-api-student-main
docker run -d \
  --name backend-api \
  --network app-network \
  -p 8080:8080 \
  -e POSTGRES_HOST=postgres-db \
  -e POSTGRES_DB=db \
  -e POSTGRES_USER=usr \
  -e POSTGRES_PASSWORD=pwd \
  my-backend-api

Vérifications :
- http://localhost:8080/departments
- http://localhost:8080/departments/IRC/students
- http://localhost:8080/students

Résultat :
- l’API Spring Boot démarre correctement
- l’application accède à PostgreSQL via le réseau Docker `app-network`
- les endpoints REST retournent les données de la base

1-5 Pourquoi a-t-on besoin d’un reverse proxy ?

Un reverse proxy sert d’entrée unique devant l’application.

Avantages :
- centraliser l’accès HTTP
- masquer les détails internes des services backend
- router les requêtes vers le bon service
- ajouter plus tard du SSL, du load balancing, du cache ou de l’authentification

---

HTTP server / Reverse proxy :

Image choisie :
- `httpd:2.4-alpine`

Fichiers ajoutés :
- `http-server/index.html`
- `http-server/reverse-proxy.conf`
- `http-server/Dockerfile`

Principe :
- Apache sert une landing page sur `/`
- Apache redirige `/api`, `/departments` et `/students` vers le conteneur `backend-api`

Commandes :
docker build -t my-http-server ./http-server
docker run -d \
  --name http-server \
  --network app-network \
  -p 8090:80 \
  my-http-server

Vérifications :
- http://localhost:8090/
- http://localhost:8090/api/?name=DevOps
- http://localhost:8090/departments/IRC/students

Résultat :
- l’application est accessible via Apache
- Apache joue le rôle de reverse proxy devant le backend Spring Boot

1-6 Pourquoi docker-compose est-il si important ?

Docker Compose permet d’orchestrer plusieurs conteneurs comme une seule application.

Avantages :
- démarrage et arrêt de toute la stack avec une seule commande
- configuration centralisée dans un seul fichier
- réseau commun automatiquement créé
- dépendances de démarrage plus simples à gérer
- configuration plus reproductible pour toute l’équipe
- plus facile à maintenir qu’une suite de longues commandes `docker run`

---

1-7 Commandes importantes docker-compose

Lancer la stack :
docker compose up -d

Builder et lancer la stack :
docker compose up -d --build

Voir les services :
docker compose ps

Voir les logs :
docker compose logs
docker compose logs -f backend-api

Arrêter et supprimer les conteneurs :
docker compose down

Arrêter et supprimer aussi les volumes :
docker compose down -v

Relancer un service précis :
docker compose up -d --build backend-api

1-8 Documentation du fichier docker-compose

Fichier :
- `docker-compose.yml`

Objectif :
- orchestrer les trois services de l’application
- n’exposer que le reverse proxy au poste hôte

Services :

1. `postgres-db`
- build à partir du `Dockerfile` racine
- variables d’environnement pour la base, l’utilisateur et le mot de passe
- volume nommé `postgres-data` pour la persistance
- healthcheck avec `pg_isready`
- non exposé au poste hôte

2. `backend-api`
- build à partir de `simple-api-student-main/Dockerfile`
- utilise `postgres-db` comme hôte de base de données
- dépend du healthcheck PostgreSQL
- port `8080` exposé seulement au réseau interne Docker
- non publié sur la machine hôte

3. `http-server`
- build à partir de `http-server/Dockerfile`
- dépend du backend
- publie uniquement `80` vers `${HTTP_PORT:-8080}` sur la machine hôte
- sert la landing page et reverse-proxy l’API

Réseau :
- réseau dédié `app-network`
- permet la communication interne entre `http-server`, `backend-api` et `postgres-db`

Volume :
- `postgres-data`
- conserve les données PostgreSQL entre deux redémarrages

Pourquoi cette approche est propre :
- la base de données et le backend restent privés
- seul Apache est accessible depuis `localhost`
- la stack complète est relançable avec une seule commande

Commande principale :
docker compose up -d --build

Accès :
- http://localhost:8080/
- http://localhost:8080/departments/IRC/students

Résultat :
- application 3-tiers fonctionnelle avec Docker Compose
- accès utilisateur uniquement via le reverse proxy
